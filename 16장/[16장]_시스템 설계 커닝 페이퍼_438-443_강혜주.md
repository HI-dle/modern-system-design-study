# 16.4 사용 사례별로 어떤 컴포넌트를 사용해야 할까?

시스템 설계에서는 적합한 컴포넌트를 선택하는 것이 성능, 확장성, 유지 관리와 관련된 중요한 판단이다.

다음은 다양한 상황에서 어떤 컴포넌트를 선택해야 하는지 정리한 내용이다.

---

## 로드 밸런서

로드 밸런서는 네트워크나 애플리케이션으로 들어오는 트래픽을 여러 서버로 고르게 분산시켜 주는 역할을 한다.

주요 사용 사례는 다음과 같다.

- **웹 애플리케이션**
    - 트래픽이 많고 사용자가 급격히 늘어날 수 있는 서비스에 사용한다.
    - 예: 이커머스 사이트, SNS, 기업 웹사이트
    - 서버 한 대가 모든 요청을 처리하지 않도록 트래픽을 분산한다.

- **데이터베이스 클러스터**
    - 데이터베이스의 읽기/쓰기 요청을 여러 서버로 분산한다.
    - 읽기 복제본을 여러 개 두고 읽기 요청을 나누어 처리할 때 유용하다.

---

## 프록시

프록시는 사용자 장치와 인터넷 사이에서 중간 역할을 한다.

사용자가 요청한 내용을 대신 가져오거나, 보안과 캐싱을 위해 사용될 수 있다.

주요 사용 사례는 다음과 같다.

- **프라이버시 및 익명성**
    - 프록시는 사용자의 IP 주소를 숨기고 다른 지역에서 접속하는 것처럼 보이게 할 수 있다.
    - 예: 지역적으로 접근이 제한된 콘텐츠를 보기 위해 사용

- **보안**
    - 일부 프록시는 유해 콘텐츠를 차단하거나 데이터를 암호화하는 등 추가적인 보안 기능을 제공한다.

- **콘텐츠 필터링**
    - 회사나 학교 같은 조직에서는 프록시를 이용해 특정 사이트나 콘텐츠에 대한 접근을 제한할 수 있다.

---

## 리버스 프록시

리버스 프록시는 인터넷과 웹 애플리케이션 서버 사이에서 중간 역할을 하며, 서버를 보호하고 트래픽을 관리한다.

주요 사용 사례는 다음과 같다.

- **전자상거래 웹사이트**
    - 많은 트래픽이 몰리는 세일 기간이나 성수기에 리버스 프록시를 사용해 서버 부하를 분산한다.

- **CDN**
    - 리버스 프록시는 콘텐츠를 캐싱하여 전 세계 각지의 콘텐츠 제공 서버로 요청을 전달한다.

- **마이크로서비스 아키텍처**
    - 복잡한 마이크로서비스 시스템에서 요청을 각 서비스로 적절히 라우팅한다.
    - 이를 통해 트래픽 관리와 서비스 구성을 더 쉽게 할 수 있다.

---

## 속도 제한기

속도 제한기는 API 남용을 보호하고, 과도한 요청으로 시스템이 영향을 받지 않도록 요청 수를 제한한다.

주요 사용 사례는 다음과 같다.

- **API 보호**
    - 한 애플리케이션이 특정 시간 동안 보낼 수 있는 API 요청 수를 제한한다.
    - 서비스 남용이나 DoS 공격을 예방하는 데 사용한다.

- **로그인 시도 제한**
    - 로그인 시도 횟수를 제한한다.
    - 비밀번호를 무작위로 반복해서 입력하는 무차별 공격을 막을 수 있다.

- **전자상거래 결제**
    - 짧은 시간 안에 과도하게 구매를 시도하는 행위를 제한한다.
    - 결제 시스템이 과부하되거나 부정 거래가 발생하는 것을 줄일 수 있다.

---

## 서킷 브레이커

서킷 브레이커는 특정 서비스나 리소스의 상태를 자동으로 감시하고, 정해진 조건에서 시스템으로 퍼지는 장애를 막는다.

주요 사용 사례는 다음과 같다.

- **마이크로서비스 아키텍처**
    - 어떤 서비스가 실패하거나 응답하지 않을 때 계속 요청을 보내면 장애가 다른 서비스로 전파될 수 있다.
    - 서킷 브레이커는 실패가 반복되는 서비스 호출을 일시적으로 차단한다.

- **외부 API**
    - 사용자는 외부 API에 장애가 생겼을 때도 시스템 전체가 영향을 받지 않기를 원한다.
    - 서킷 브레이커를 통해 장애가 있는 외부 API 호출을 잠시 막을 수 있다.

---

## API 게이트웨이

API 게이트웨이는 마이크로서비스 아키텍처에서 모든 API 요청을 중앙에서 관리하는 역할을 한다.

주요 사용 사례는 다음과 같다.

- **단일 진입점**
    - 모든 API 요청을 한 곳에서 받아 처리한다.
    - 클라이언트가 각 서비스의 세부 정보를 몰라도 쉽게 접근할 수 있다.

- **요청 라우팅**
    - API 요청을 적절한 백엔드 서비스로 전달한다.

- **인증 및 권한 부여**
    - 승인된 사용자만 특정 기능에 접근할 수 있도록 한다.

- **모니터링 및 분석**
    - API 트래픽을 관찰하고 사용 패턴을 분석한다.
    - API 사용 현황에 대한 유용한 정보를 얻을 수 있다.

---

## 메시지 큐

메시지 큐는 시스템 간의 통신을 비동기 방식으로 처리한다.

각 시스템을 서로 독립적으로 만들고, 작업을 안정적으로 처리하는 데 사용한다.

주요 사용 사례는 다음과 같다.

- **이커머스 주문 처리**
    - 고객이 주문하면 주문 정보를 메시지 큐에 보낸다.
    - 이후 워커 서비스가 큐에서 메시지를 받아 결제, 재고 확인, 배송 등록을 처리한다.
    - 주문 처리 과정을 안정적으로 진행할 수 있다.

- **작업 처리**
    - 대용량 이미지나 비디오 처리 같은 무거운 작업을 비동기적으로 처리한다.
    - 메인 애플리케이션은 다른 사용자 요청을 계속 처리할 수 있다.

- **소셜 미디어 피드**
    - 사용자가 글을 올리면 새 글 정보를 메시지 큐에 저장한다.
    - 피드 서비스가 이를 가져와 팔로워들의 피드를 갱신한다.

---

## CDN

CDN은 전 세계에 분산된 서버를 통해 콘텐츠를 사용자와 가까운 위치에서 빠르게 제공한다.

주요 사용 사례는 다음과 같다.

- **웹사이트 및 웹 애플리케이션**
    - 이미지나 웹 페이지 같은 정적 콘텐츠를 CDN을 통해 제공한다.
    - 사용자와 가까운 서버에서 콘텐츠를 제공해 로딩 속도를 줄인다.

- **스트리밍 서비스**
    - 영화나 음악 스트리밍 서비스는 CDN으로 콘텐츠를 빠르게 전달한다.
    - 사용자가 영화를 볼 때도 빠르고 안정적으로 서비스를 사용할 수 있다.

- **소셜 미디어 플랫폼**
    - 사용자가 많은 소셜 미디어 플랫폼에서는 이미지와 동영상을 CDN으로 효율적으로 전송한다.
    - 사용자 경험을 높일 수 있다.

# 16.5 사용 사례별로 어떤 프로토콜을 사용해야 할까?

각 프로토콜은 서로 다른 특성을 가진다.

따라서 사용 사례에 따라 적절한 프로토콜을 선택해야 한다.

---

## 프로토콜 특징 비교

| 특징 | HTTP | SSE | 웹소켓 |
|---|---|---|---|
| 통신 모델 | 요청-응답 | 단방향 서버 → 클라이언트 | 양방향 |
| 연결 타입 | 단기 연결 | 장기 연결 | 장기 연결 |
| 데이터 형식 | 텍스트, HTML, JSON 등 | 텍스트 이벤트 스트림 형식 | 텍스트 및 바이너리 |
| 사용 예시 | 웹 페이지, REST API | 실시간 업데이트, 알림 | 실시간 채팅, 게임, 금융 티커 |
| 지연 시간 | 높음 | 낮음 | 매우 낮음 |
| 확장성 | 높음 | 중간 | 중간 |
| 자동 재연결 | 지원 안 함 | 지원 | 애플리케이션 수준에서 관리 필요 |
| 프로토콜 오버헤드 | 높음 | 낮음 | 낮음 |
| 웹 브라우저 지원 여부 | 모든 웹 브라우저 | 최신 웹 브라우저 | 최신 웹 브라우저 |

---

## 사용 사례별 권장 프로토콜

| 사용 사례 | 권장 프로토콜 | 선택 이유 |
|---|---|---|
| 정적 콘텐츠 전송 | HTTP | 간단한 요청-응답 방식으로 널리 지원된다. |
| RESTful API | HTTP | 상태가 없으며 백엔드 통신에 널리 사용된다. |
| 폼 데이터 전송 | HTTP | 폼 데이터를 처리하는 표준적인 방식이다. |
| 파일 전송 | HTTP | 대용량 파일 업로드와 다운로드에 효율적이다. |
| 실시간 알림 | SSE | 서버에서 클라이언트로 데이터를 보내기 좋다. |
| 실시간 피드 | SSE | 실시간 데이터를 효율적으로 지속해서 보낼 수 있다. |
| 모니터링 대시보드 | SSE | 서버에서 클라이언트로 지속적인 상태 업데이트를 보낼 수 있다. |
| 간단한 채팅 및 메시지 전달 | SSE | 서버에서 클라이언트로 간단한 메시지를 단방향으로 보내기 적합하다. |
| 온라인 게임 | 웹소켓 | 지연 시간이 매우 짧고, 서버와 클라이언트 간 양방향 통신이 가능하다. |
| 실시간 채팅 | 웹소켓 | 양방향 메시지를 실시간으로 주고받는 데 적합하다. |
| 협업 도구 | 웹소켓 | 실시간 문서 편집 같은 양방향 협업에 유리하다. |
| 금융 관련 애플리케이션 | 웹소켓 | 짧은 지연 시간을 바탕으로 실시간 통신하는 데 적합하다. |
| IoT 애플리케이션 | 웹소켓 | 기기와 서버 간 지속적인 데이터 주고받기에 적합하다. |

# 16.6 사용 사례별로 어떤 솔루션을 적용해야 할까?

안정적이고 확장 가능한 시스템을 만들려면 각 설계 과제에 적합한 해결 방법을 선택해야 한다.

각 과제마다 효과적인 전략과 기술이 다르기 때문에, 요구 사항에 맞는 해결 방법을 적용해야 한다.

---

## 설계 과제별 해결 방법

| 설계 과제 | 설명 | 선택 가능한 방법 |
|---|---|---|
| 높은 쓰기 처리량 관리 | 로그, 실시간 분석 등 매우 높은 쓰기 빈도를 처리해야 하는 시스템 관리 | WAL, 샤딩, 비관계형 데이터베이스 |
| 데이터 일관성 보장 | 분산 시스템 내에서 일관성 유지 | 분산 트랜잭션, 최종 일관성, 충돌 해결 |
| 낮은 지연 시간 요구 사항 | 응답 지연 시간을 최소화하는 것 | 인메모리 데이터베이스, 캐싱, 에지 컴퓨팅 |
| 확장성 | 부하가 늘어나더라도 처리할 수 있도록 시스템 확장 | 수평 확장, 로드 밸런싱, 마이크로서비스 아키텍처 |
| 장애 허용성 | 시스템에 장애가 발생하더라도 계속 운영되도록 보장 | 데이터 복제, 장애 복구 메커니즘, 서킷 브레이커 |
| 데이터 파티셔닝 | 여러 노드에 데이터를 분산하여 저장 | 해시 파티셔닝, 범위 파티셔닝, 일관된 해싱 |
| 검색 성능 향상 | 빠르고 정확한 검색 결과 제공 | 역인덱스 검색 엔진, 캐싱 |
| 갑자기 튀는 듯이 급격히 몰리는 트래픽 처리 | 이벤트나 세일 등 갑작스러운 트래픽 증가 관리 | 자동 확장, 부하 평준화, CDN 활용 |
| 분산 락 | 분산 시스템에서 공유 리소스에 대한 접근 조율 | 분산 락 관리자, 주키퍼, 레디스 |

# 16.7 요약

이 장에서는 시스템 설계 면접에서 좋은 결과를 얻으려면 어떻게 체계적으로 접근해야 하는지 살펴보았다.

구체적으로는 다음 내용을 다루었다.

- 문제를 명확하게 이해하는 방법
- 요구 사항을 정리하는 방법
- API를 설계하는 방법
- 아키텍처 다이어그램을 효과적으로 그리는 방법
- 데이터 저장소를 설계하는 방법
- 데이터 구조를 선택하는 방법
- 구성 요소, 프로토콜, 솔루션을 고르는 기준

또한 좋은 주요 시스템 설계 요소를 검토했다.

- 확장성
- 신뢰성
- 낮은 지연 시간
- 캐싱
- 알고리즘

이 장에서 다룬 구체적인 팁과 방법을 활용하면 시스템 설계 면접을 더 자신 있게 준비할 수 있다.

시스템 설계 면접에서 중요한 것은 정답 하나를 맞히는 것이 아니다.  
문제를 얼마나 명확히 이해하고, 설계 선택에 따른 장단점을 얼마나 잘 설명할 수 있는지가 중요하다.

앞으로도 다양한 상황에서 직접 시스템을 설계해 보고, 실제 사례를 분석하며 연습하는 과정이 필요하다.
